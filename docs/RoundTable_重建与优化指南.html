2. 这个项目目前最清晰的整体轮廓

2.1 产品定位

  • 产品名称：RoundTable / 圆桌思辨。
  • 核心目标：为中国小学生提供 AI 引导的思辨讨论环境。
  • 产品本质：不是群聊产品，而是“有主持、有秩序、有回合、有点评、有启发”的讨论训练平台。

2.2 用户与参与者模型

  • 真人学生：讨论中心，系统必须围绕其观点展开。
  • 主持人“李老师”：负责开场、点名、点评、收尾，总控讨论秩序。
  • AI 同学角色：不同思维风格和表达风格，参与讨论。
  • 思想家角色：从哲学、社会、科学等角度补充讨论。

2.3 当前工程分层

层技术职责
前端Flutter Web主页、讨论页、设置页、沉浸式 UI、字幕、语音播放、交互控制

讨论引擎AutoGen SelectorGroupChat主持人驱动的多角色发言选择与协作生成
语音层多 provider TTS/ASR老师与学生语音、浏览器/服务端识别、设置与测试链路

3. 目前项目的关键架构

3.1 Backend

  • 入口：FastAPI 应用位于 backend/app/main.py，负责 API 路由、CORS、静态文件挂载、启动期预热。
  • 配置中心：backend/app/config.py，统一管理 LLM、TTS、ASR、服务 URL、provider 默认值与运行时读取逻辑。
  • 讨论编排：backend/app/core/turn_scheduler.py + backend/app/core/floor_manager.py。
  • 角色构建：backend/app/agents/moderator.py、backend/app/agents/virtual_character.py、backend/app/agents/human_proxy.py。
  • 接口层：backend/app/api/v1/router.py 汇总 sessions、config、voice、websocket、topics、characters、thinkers 等接口。
  • 语音工厂：backend/app/voice/factory.py 及各 provider 实现，支持多种 TTS/ASR。
  • 持久化观测：backend/app/core/meeting_history.py，将 session 过程写入 backend/runtime/meeting_history。

3.2 Frontend

  • 应用入口：frontend/lib/main.dart → frontend/lib/app.dart。
  • 主页：frontend/lib/features/home，负责话题进入、自由话题、预热配置与角色入口。
  • 讨论页：frontend/lib/features/session，负责圆桌 UI、回合状态、字幕、TTS、PTT、历史记录、金句等。
  • 设置页：frontend/lib/features/settings，负责 LLM / ASR / TTS provider 配置、连接测试、runtime 同步。
  • 状态管理：Riverpod + 本地设置持久化。
  • 服务层：REST API Client、WebSocket Client、Speech Services。

3.3 构建与发布方式

  • 不是前后端分离部署的浏览器开发模式优先，而是通过 build_web.sh 将 Flutter Web 构建产物复制到 backend/static。
  • 因此浏览器最终访问的是后端托管的静态文件，前端改动后必须重新 build 才能在 8001 生效。

4. 当前项目最核心的原则与规则

4.1 讨论机制规则

  • 老师必须开场，先介绍背景与问题，再安排后续发言。
  • 真人学生是绝对核心，不允许被边缘化。
  • 真人学生每次发言后，老师必须立即回应，并且引用其具体表述。
  • 每轮只允许一人发言，不能把它做成群聊抢话模式。
  • 首轮阶段禁止互引式表达，例如“上一位同学说得对”。
  • 讨论接近结束时，老师要进行两轮征询，再自然收尾。

4.2 角色一致性规则

  • 角色必须知道自己是谁，不能错把自己当成其他角色。
  • 主持人要保持第一人称“我”，不能第三人称自称“李老师觉得……”。
  • 点名、引用、点评必须尽量使用准确的说话人归属。

4.3 小学生适龄与安全规则

  • 内容应适合小学生，但不能幼稚化到破坏真实讨论感。
  • 安全过滤主要拦截明确不适宜内容，而不是把所有复杂话题都删掉。
  • 允许开放型思辨，但表达必须温和、清楚、可理解。

4.4 语音与时序规则

  • TTS/ASR provider 可切换，设置页与讨论页必须共享同一运行时事实来源。
  • 讨论页要求字幕、语音、回合状态严格协同。
  • 当前开场节奏要求：中心提示“老师准备中……” → “开始讨论” → 老师字幕出现 → 300ms 后老师开口。
  • 同一角色在同一轮中，不应把刚刚已经播过的完整句子再重复播一遍。

6. 如果你让我“最快重建”，我建议采用的落地顺序

  1. 先搭后端骨架：FastAPI、配置中心、话题/角色数据加载、session CRUD、WebSocket 通道。
  2. 再搭讨论引擎：主持人 Agent、虚拟角色 Agent、真人学生桥接、SelectorGroupChat、FloorManager 状态机。
  3. 随后搭前端主流程：主页进入 → 创建 session → 连接 WebSocket → 最简讨论页可运行。
  4. 再补语音：先 EdgeTTS / 浏览器 ASR 跑通，再逐步加 OpenVoice、FunASR 与设置同步。
  5. 补观测与可诊断性：会议记录、配置 health、历史发言记录板。
  6. 最后做交互细节与回归测试：字幕时序、回合节奏、重复发言保护、设置页测试链路。

7. 目前这个项目下一步值得优化提升的方向

7.1 产品体验层

  • 讨论前准备流程：在开始前加入“角色确认、语音检查、话题确认、学生人数确认”的轻量向导，减少会话启动后才发现配置不对的问题。
  • 会话结束产物：目前已有金句与历史记录，下一步可补“讨论摘要、观点分歧、学生亮点、老师建议”等结构化总结卡片。
  • 自由话题可视反馈：让用户更明确看到自由话题已被提炼成什么正式讨论题目。

7.2 AI 讨论质量层

  • 建立系统化评测：对主持人开场、点名准确率、用户中心化、重复率、错认身份率做可回归评估，而不是只靠人工试跑。
  • 提示词版本化：将 moderator / virtual character / thinker 的提示词与规则做版本管理和差异记录，便于回滚与比较。
  • 角色发言去重与压缩：目前已处理部分流式重复，后续可继续减少长句、套话、空洞复述、无效表演化表达。

7.3 语音与多模态层

  • 服务端 TTS 预取缓存：已有方向，但可以进一步做多句缓存、命中统计和按 provider 的缓存策略。
  • ASR 统一上传格式：把浏览器 WebM、本地 WAV、网关代理等路径进一步标准化，减少 provider 适配分叉。
  • 会话内语音诊断：把当前 provider、voice、延迟、失败重试信息更直接显示在讨论页开发视图里。

7.4 工程架构层

  • 配置模型统一：把“环境变量配置、运行时配置、设置页表单值、前端本地缓存”之间的映射进一步收束成单一事实来源。
  • 讨论编排与语音编排解耦：FloorManager 现在承担很多职责，后续可以把发言选择、文本后处理、语音发射拆分成更清晰的层。
  • 会话恢复与回放：让断开连接后的 session 可以恢复，而不是主要依赖内存态与历史文件诊断。

7.5 可观测性与运维层

  • 统一会话监控：现在监控有一部分是 runtime 文件，一部分是页面内存。后续可统一成后端可查询的会话诊断 API。
  • 结构化指标：增加 token、轮次、平均响应时间、TTS 命中率、ASR 成功率、用户发言占比等指标。
  • 错误分级：区分 provider 配置错误、模型输出异常、会话状态错乱、网络中断等不同故障类别。

7.6 内容与运营层

  • 话题编辑后台：让话题 YAML 不再只靠手工维护，可以做导入、标签、难度级别、适龄建议。
  • 角色模板管理：统一维护角色人设、口头禅、发言长度、质疑风格、适用年龄层。
  • 思想家资源扩展：把思想家模板从静态 YAML 升级为更易扩展的数据资产。
